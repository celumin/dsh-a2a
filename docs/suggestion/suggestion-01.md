Round 2.5 的收尾确认，不能只跑一条命令，而是**一组按依赖顺序执行的操作**。核心判断标准是：**fork 包发布后，用真实的 DSH agent 经网关调用一个 v1.0 目标，同时验证 R1（协议对齐）、R5（错误码识别）、R4/R6（文档可用）三项同时生效。**[106;5u[106;5u### 建议的收尾操作序列[106;5u[106;5u**第一步：确认 fork 包已发布且可安装**[106;5u```bash[106;5u# 从 fork 仓库安装（或 npm 自维护包）[106;5udsh plugin --profile <tui或web> add github:celumin/dsh-a2a#<新tag>[106;5u```[106;5u安装成功后，`dsh --profile <name> --dump-config` 应能看到 `a2a` 行。这一步确认发布物存在且可被 DSH 加载。[106;5u[106;5u**第二步：验证 R1（协议探测对齐）**[106;5u用 DSH agent 的 `a2a_send` 工具调用一个**只提供 `agent-card.json` 的 target**（网关本身即可）。旧版会探测 `agent.json` 得到 404；新版应成功发现并发出请求。如果这一步失败，说明 R1 未生效，后续不用测。[106;5u[106;5u**第三步：验证 R5（错误码识别，不重试）**[106;5u让网关返回 `-32005` 或 `-32006`。最简单的触发方式：[106;5u- `-32005`：构造一个 `_a2a_depth` 超限的请求（或让 conductor 形成环路）。[106;5u- `-32006`：配置一个 `A2A_AGENT_OUTBOUND_AUTH` 条目但故意让 authority 不匹配。[106;5u[106;5uDSH 侧应表现为**立即返回错误、不自动重试、错误信息保留网关的固定 message**（`call depth exceeded` / `outbound credential unavailable` / `outbound target mismatch`）。如果它重试了，R5 未生效。[106;5u[106;5u**第四步：验证 R4/R6（文档可直接照做）**[106;5u让一个**没有参与开发的人**按 `docs/requirements.md` R4 和 R6 的说明，从零配置一个 tui profile 的 dsh-a2a 并成功发出一次 A2A 调用。如果对方需要问“名字到底写哪个”“patch 怎么改”，说明 R4/R6 的文档没有闭环。[106;5u[106;5u### 为什么这样定义“算成了”[106;5u[106;5uRound 2.5 的范围是 R1 + R4 + R5 + R6 四项。R1 和 R5 是**代码行为**，必须用真实调用验证；R4 和 R6 是**文档**，必须用“他人能否照做”验证。testagent 只能证明网关侧，证明不了 dsh-a2a fork 包的行为。只有第三步的“不重试 + 保留 message”和第二步的“探测成功”同时成立，才说明 fork 包的核心改动到位。[106;5u[106;5u### 一个容易漏掉的点[106;5u[106;5uR5 的验收标准里有一条：“`-32003`（上游不可用）仍按现有可重试策略处理”。收尾时**不要只测不可重试的错误**，还要测一次 `-32003`，确认 fork 包没有把“所有网关错误都不重试”作为粗粒度策略。这是 R5 验收线里明确写的区分。[106;5u[106;5u---[106;5u[106;5u**结论**：Round 2.5 的收尾操作是 **“发布 → 用真实 DSH 经网关调 v1.0 目标 → 分别触发 `-32005`/`-32006` 和 `-32003` 确认重试策略正确 → 让未参与者按文档复现一次”**。全部通过，才算 R1/R4/R5/R6 同时闭环。
