- **v2**：复核源码后纠正根因（URL 丢失 base path、尾斜杠、method 写死），新增 v1.0 报文适配。
- **v3**：确认适配进入 0.4.0，边界四件事；拆开"默认版本"与"降级"；补安全边界。
- **v4**：跨源放行改 origin 精确匹配 + WARN；降级 detail 双侧；未知状态可观测；`metadata.kind/from` 不受降级影响；缓存不做，短 TTL 转 R7。

  7. 明确**出站 message 形状不变**（role/kind 仍是 v0.3 形），"v1.0 适配"只覆盖响应侧；严格 ProtoJSON 服务端不在本轮范围。

## 1. 为什么要改（纠正后的根因）

2026-10-22 的结论是"`a2a_send` 按 v0.3 探测 `agent.json`，网关 404"。复核源码后，这个结论是错的：`A2aClient.card()` 自 v0.1.0 起就是 `agent-card.json` 优先、`agent.json` 回退（`src/client.ts:143-144`）。

真实缺陷有四处，都在客户端：

1. **卡片 URL 丢失 base path**：`cardUrl` 是 `origin + wellKnown`（`src/client.ts:85`）。target 为 `http://gw:9090/a2a/pi-gw-agent` 时请求 `http://gw:9090/.well-known/agent-card.json`，而网关只在 `/a2a/{id}/.well-known/agent-card.json` 挂载（`a2a-way/internal/registry/handlers_read.go:21`）。
2. **RPC URL 多一个尾斜杠**：`rpcUrl` 为 `path + '/'`（`src/client.ts:79-84`），发出 `POST /a2a/{id}/`；网关注册的是 `POST /a2a/{agentID}`（`a2a-way/internal/bridge/handlers.go:131`，chi，无 `RedirectSlashes`）。
3. **method 名写死**：`send()` 固定 `message/send`（`src/client.ts:187`）、`sendStream()` 固定 `message/stream`（`src/client.ts:241`）；Pi 只认 `SendMessage`/`GetTask`（`pi-a2a/extensions/net.ts:368-371`）。
4. **响应形状只认 v0.3**：v1.0 的 `SendMessage` 返回 `{ "task": {...} }`（`net.ts:433`），状态是 `TASK_STATE_*`（`net.ts:397`），part 用成员名判别（`{ text }`，无 `kind`，`net.ts:589`）。客户端强转 `A2aTask` 并读 `status.state`（`src/client.ts:212-225, 372`），第一跳就会 TypeError 或永不到终态。网关原样透传上游响应体（`a2a-way/internal/bridge/forward.go:700`），必然命中。

另外两处促成变更：

- **参数约定**：A2A 0.3 规范用 `params.id`；`{taskId}` 只是本插件的旧约定，服务端为了兼容两种都收（`src/server.ts:497-503`）。
- **流式判断**：`sendForText` 在"卡片取不到"时也会走流式（`src/client.ts:334-343`），与"v1.0 一律同步"冲突。

## 2. 目标与非目标

**目标**

- target 的三种形态——origin 根、路径基址（`{origin}{path}`）、卡片 URL（以 `/.well-known/...` 结尾）——都能找到卡片与正确的 RPC 端点。
- 按卡片协商 v1.0 / v0.3 的方法名，并归一两种**响应**形状；内部 `A2aTask` / `Message` / `TaskEvent` 形状不变（例外见下）。
- 端点选择有明确的授权规则：同源 + 路径作用域，跨源需独立白名单，Bearer 不越界。
- 工具输出让模型看得见错误码与可重试性；超时给出结构化说明。
- README 让没参与开发的人从零配好。
- 以 `0.4.0` 发布到 npm，并推 fork 分支。

**适配边界**

响应侧四件：

1. `SendMessage` 的 `{ task }` / `{ msg }` 解包；`GetTask` 的 `{ task }` 也容忍；
2. `TASK_STATE_*` → 内部状态，未知值进 `'unknown'` 并保留 `rawState`；
3. part 缺 `kind` 时按成员判别；
4. `GetTask` 的 params 统一 `{ id }`。

必要的管线修复（不做则主验收线不成立）：

5. `getTask` / `cancelTask` 也先加载并协商卡片（懒加载，复用实例缓存）；
6. 流式启用条件收紧（见 §3.4.4）；
7. `A2aClientOptions` 增加 `logger` 与 `fetchImpl` 测试缝；`AgentCard` 类型补可选字段、`TaskState` 补 `'auth-required'` / `'unknown'`（见 §3.5）。

**非目标**

- **不改出站 message 形状**：仍发 `role: "user"`、`kind: "message"`、`parts[].kind`。Pi 宽容（`net.ts:383-391`、`extractText` 只读 `.text`）；**严格 ProtoJSON v1.0 服务端（要求 `ROLE_USER`、无 `kind`）不在本轮范围**，README 写明。
- 不做 v1.0 流式事件（`SendStreamingMessage`、`{statusUpdate}`、`{artifactUpdate}`）。
- 不改自身 server 的版本声明（仍 `0.3.0`）与入站方法集。
- 不在网关侧做 method 名转换；不修网关"接口条目恒为 1.0"（见 §6）。
- 不新增 `agent.json` 别名（2026-10-24 已决）。
- 不实现 mDNS（R3）。
- 不做卡片发现的进程级缓存（短 TTL 列为 0.5.0 候选，`docs/requirements.md` R7）。
- 不改 `metadata.kind` / `metadata.from` 的语义。

## 3. 设计

### 3.1 target 归一

`normalizeTarget(baseUrl) → { origin, path, givenCardUrl? }`：

- URL 解析失败 → 直接报错 `invalid target url`。
- **含 query 或 fragment → 报错** `target must not contain query or fragment`（JSON-RPC 端点不应带查询串；现在 `normalize()` 会静默丢掉，`src/client.ts:80-82`）。
- 若 path 以 `/.well-known/agent-card.json` 或 `/.well-known/agent.json` **结尾** → `givenCardUrl` = 原 URL，`path` = 去掉该后缀的路径（可为空）。
- 否则 path = 去掉尾部 `/` 的 pathname（根为 `''`）。
- 端口、大小写按 `URL` 规范化。

**术语**：*卡片 URL* = `……/.well-known/agent-card.json`；*服务 URL* = 卡片里的 `url` / `supportedInterfaces[].url`（如 Pi 的 `/rpc`）。**服务 URL 不作为 target 入参**——它无法与"路径基址"区分。README 写明。

### 3.2 卡片发现

候选（去重后按序）：

1. 给定卡片 URL（仅当 `givenCardUrl` 存在）；否则 `{origin}{path}/.well-known/agent-card.json`。
2. `{origin}{path}/.well-known/agent.json`。

**不再尝试 origin 根候选**：路径基址的 origin 根可能挂着无关应用，带 Bearer 去打会泄漏 token（review M9）。origin 根场景下 `path === ''`，候选 1/2 本来就是根，行为不变。

每个候选：

- **不走重定向**：`fetch(..., { redirect: 'manual' })`；任何 3xx 记为该候选失败（`redirect not followed: <status>`），继续下一个（review M8）。
- **不要用 `headers()` 带 Bearer 去打候选**？——卡片 GET 需要鉴权时仍要带，但只在"该候选 URL 落在 target 的 `clientAllowPatterns` 作用域内"时带；否则不带 token 试一次（多数公开卡片无需鉴权）。
- 超时：`min(5_000, 剩余预算)`（见 §3.6 预算）。

取第一个 2xx 且 JSON 能解析出服务地址（`url` 或 `supportedInterfaces[].url`）的响应；解析失败继续下一个。

全部失败 → **降级**（§3.4.2）。错误信息保留每个候选的失败原因（状态码/解析错误），不含 token。

卡片结果缓存在 `A2aClient` 实例内（含"无卡片"这个结论，避免同一实例反复试）。客户端按工具调用创建（`src/tools.ts:90-96`），所以每次 `a2a_send` 仍会付 1–2 次 GET；0.4.0 接受，不做进程级缓存（R7）。

### 3.3 RPC 端点与授权

**端点解析**（有卡片时）：

1. `supportedInterfaces[]` 中 `protocolBinding`（大小写不敏感）为 `JSONRPC` 的第一条：取其 `url` **与** `protocolVersion`（同一条目，不跨条拼装）；
2. 否则顶层 `url` 与顶层版本字段；
3. 卡片给的相对 URL（`/rpc`、`//host/rpc`）以卡片 URL 为基准解析；
4. 去掉尾部 `/`（除非就是 `'/'`）；
5. 无可用端点 → 回退 `{origin}{path}`（`path === ''` 时 `{origin}/`）。

**授权算法**（`P1 = clientAllowPatterns`，`P2 = clientCardEndpointPatterns`）：

```
E = 卡片端点（已解析）
if E 与 target 同源（scheme+host+port 精确相等）:
    if matchesAllowlist(P1, E):             # 现有语义：host/port + 路径前缀
        采用 E
    else:
        忽略 E → 回退 {origin}{path}，WARN `card endpoint outside clientAllowPatterns`
else:
    if matchesCardEndpointAllowlist(P2, E):
        采用 E，WARN `card endpoint cross-origin allowed by clientCardEndpointPatterns`
    else:
        忽略 E → 回退 {origin}{path}，WARN `card endpoint cross-origin ignored`
```

- **`P1` 的路径作用域对同源端点同样生效**：target 是 `https://host/tenantA/`、卡片端点指向 `https://host/tenantB/admin` 时，同源但越界 → 忽略并回退。这是 review B2 的核心修正：不能因为"同源"就放行整站。
- **`P2` 是新配置，默认 `[]`（全拒）**，语义为**完整 URL 前缀**（scheme+host+port 精确，path 按边界匹配：`https://x/rpc` 匹配 `https://x/rpc` 与 `https://x/rpc/...`），**不做通配、`*` 不生效**。它是运维的显式选择，不是卡片能自己争取到的。
- **Bearer 只发往"采用的端点"**；被忽略的跨源端点一个字节都不发（连卡片 GET 的候选都不碰跨源）。
- WARN 只记录 **origin**（scheme+host+port）与原因码，不记录 path/query、不回显卡片 URL。
- 回退端点自身的授权由 target 的 `P1` 决定（用户输入已过 `checks`，`src/tools.ts:83-88`）。

**Pi 的前置条件**：Pi 卡片广告的是 `http://<lanIp>:<port>/rpc`（`pi-a2a/extensions/net.ts:546`）。target 必须用**同一个 host**（例如 `http://192.168.10.x:PORT`），否则视为跨源 → 回退失败。README 与验收都写明；不想对齐 host 就配 `clientCardEndpointPatterns`。

### 3.4 method 协商

#### 3.4.1 版本来源与判定

按 §3.3 的端点解析顺序取版本：JSONRPC 接口条目的 `protocolVersion` → 顶层 `protocolVersions[]` 首个 → 顶层 `protocolVersion`。

判定：trim、去掉前导 `v`、正则 `^(\d+)(?:\.(\d+))?`：

- major `1` → **v1.0**
- major `0` → **v0.3**
- 其他（`2.0`、空、无法解析）→ **无可用声明**，走 §3.4.2 默认版本。

#### 3.4.2 默认版本（卡片在、无可用声明 → v0.3）

触发：卡片取到了，但版本声明缺失/无法解析。
行为：按 **v0.3**（`message/send` / `tasks/get` / `tasks/cancel`）。

> **本文档修正了早期"默认 v1.0"的笔误**：那句把 `message/send` 误当成 v1.0 方法名。真实对应是 v1.0 → `SendMessage`；默认值定为 v0.3。

#### 3.4.3 降级行为（取不到卡片 → 输入路径 + v0.3）

触发：§3.2 所有候选失败。
行为：端点 `{origin}{path}`，版本 v0.3，不使用任何卡片派生值。
**降级不改报文内容**：`metadata.kind` / `metadata.from` 照常写入——降级只影响"用哪个端点、哪种方法"，不是"最小报文"（丢了 `kind`，Pi 只入库不处理）。

> 与 §3.4.2 的区别：**卡片在、没版本** vs **卡片不在**；触发条件不同、测试用例不同。

#### 3.4.4 方法表

| 操作 | v1.0 | v0.3 |
| ---- | ---- | ---- |
| 发送 | `SendMessage` | `message/send` |
| 流式 | **不启用** | `message/stream` |
| 轮询 | `GetTask`，params `{ id }` | `tasks/get`，params `{ id }` |
| 取消 | `CancelTask`，params `{ id }` | `tasks/cancel`，params `{ id }` |

- **两个版本的 `GetTask` / `CancelTask` 都发 `{ id }`**。A2A 0.3 规范就是 `params.id`；本插件旧约定是 `{taskId}`，服务端两种都收（`src/server.ts:497-503`）——但规范型第三方只认 `id`。
- 流式启用条件：`card !== undefined && version === 'v0.3' && card.capabilities?.streaming === true`。**卡片取不到时一律同步**（修复 `src/client.ts:334-343` 的 `card === undefined` 分支）。
- `X-A2A-Version` 只随 RPC 请求发送，格式固定 `1.0` / `0.3`（主.次）；卡片 GET 不带。若对端因卡片 GET 缺版本头而拒绝，视为该候选失败（不是神秘错误）。
- 不做静默换名重发：`-32601` 原样报错，detail 附"卡片声明 vX、已用方法 Y"，避免重复投递。

`getTask` / `cancelTask` 也从同一份缓存卡片取端点与方法（懒加载 `ensureCard()`）；否则 `a2a_task_status` 会在超时后打到 `{origin}/` 并 `-32601`。

### 3.5 响应适配

内部模型形状不变，唯一例外是状态类型：

- `protocol.ts`：`TaskState` 增加 `'auth-required'` 与 `'unknown'`；`TaskStatus` 增加可选 `rawState?: string`；`TERMINAL_STATES` 不变（两者都不终态）。
- `AgentCard`：`url` 与 `protocolVersion` 改为可选；新增 `protocolVersions?: readonly string[]`（Pi 两者都不给，`net.ts:540-550`）。`buildAgentCard` 产物不变。

**入站归一**

- `SendMessage`：`{ task }` → Task；`{ msg }` → 包装为 completed Task（沿用现有的裸 Message 处理，`src/client.ts:198-210`）；裸 Task 直接收。
- `GetTask` / `CancelTask`：裸 Task；也容忍 `{ task }`。
- 状态映射：9 个 `TASK_STATE_*` → 小写内部值；`AUTH_REQUIRED` → `'auth-required'`；`UNSPECIFIED` 与未知枚举 → `'unknown'`，原值进 `rawState`。
- part：缺 `kind` 时按成员判别（`text` / `data` / `url` / `file`）。

**停止轮询的条件**：终态（`completed|failed|canceled|rejected`）、`input-required`、`auth-required`、`unknown`。后三者立即返回任务，不空转到超时（review M7）。

**超时**：到 deadline 仍非上述状态 → 抛 `A2aTimeoutError`（`code = -1`，`retryable = true`），message 含 `最后一次看到的状态是 <state|rawState>，task_id=<id>`。工具层把它渲染成 detail，不再出现 `发送失败：undefined`。

### 3.6 错误分类与工具输出（R5）

- `A2aRpcError.code` → `retryable`：`-32005` / `-32006` → `false`；`-32003` → `true`；传输/超时/重定向/HTTP 状态（`code = -1`）→ `true`；其他码省略两个字段。
- **4xx 响应体是 JSON-RPC error 时按 JSON-RPC 解析**（保留 `code`/`message`），不降级成 `HTTP <status> <text>`（`src/client.ts:126-129`）；200 但非 JSON → `invalid JSON-RPC response`（不是裸 `SyntaxError`）。
- 嵌入 detail 的响应体截断到 2KB，避免把大段不可信内容塞进模型上下文。
- `a2a_send` / `a2a_task_status` / `a2a_cancel` 失败时输出可选的 `error_code`（number）与 `retryable`（boolean）；`detail` 恒有值。
- `-32003` 的 `retryable=true` 只表示"可以重试"，不鼓励重发 `kind=request`（可能重复副作用）；有 task_id 时一并输出。
- **不引入自动重试**。

### 3.7 文档（R4 / R6）

README：

- 配置入口 `cordis.patch.yml` 的 `a2a` 行；patch **整体替换** `config`；旧 `a2a.json` 标注"已过时"。
- web / tui 两份可复制示例；tui 显式 `provider` / `model`。
- 密钥 `env:A2A_TOKEN`；web 面板的 base URL / Bearer 存浏览器 storage。
- web + tui 同跑的端口冲突与 `context-sessions.json` 覆盖。
- **target 三种形态**与"不要把服务 URL 当 target"；Pi 的 host 必须与 `lanIp` 一致。
- `clientCardEndpointPatterns` 的语义（完整 URL 前缀、默认空、`*` 不生效）与使用场景。
- 名字一致性：`peerName` / 未来 mDNS `name` / 网关 caller（例：`dsh-agent-lenovo`、`pi-gw-agent`）。
- 调用 Pi 这类投递型 agent 用 `kind=request`；`kind=message` 只入库。
- 已知限制：出站仍是 v0.3 形状；严格 ProtoJSON v1.0 服务端不在本轮支持。

| 3 | `http://<lanIp>:<port>`（host 与卡片一致） | 1.0 @ `/rpc` | `SendMessage` → `/rpc` | `kind=request` → working → `GetTask {id}` → completed |
| 4 | v1.0 target，`streaming:true` | 1.0 | `SendMessage`（**不是** `SendStreamingMessage`） | 同步返回 |
| 5 | v0.3 target，`streaming:true` | 0.3 | `message/stream` | SSE 事件序列 |
| 6 | v0.3 target，`streaming:false` | 0.3 | `message/send` | 裸 Task |
| 7 | 卡片在、无版本 | 无声明 | `message/send`（§3.4.2） | 通 |
| 8 | 无卡片、路径基址 | 无 | `message/send` → `{origin}{path}`，detail 含 `RPC 失败：…；卡片发现失败：…` | 通或结构化失败 |
| 9 | 跨源端点，P2=`[]` | 1.0 @ 别的 host | 忽略端点 → 回退 target 路径；**跨源 host 收不到任何请求** | WARN `…cross-origin ignored` |
| 10 | 跨源端点，P2=`https://other/rpc` | 同上 | `SendMessage` → `https://other/rpc`，**带 Bearer** | WARN `…allowed by …` |
| 11 | 同源但路径越界（target `/tenantA`，端点 `/tenantB`） | 1.0 | 忽略端点 → 回退 `/tenantA` | WARN `…outside clientAllowPatterns` |
| 12 | 任一端点返回 302 | 卡片 GET 302 | 该候选失败（不跟随） | 走下一候选/降级 |
| 13 | 网关 `-32005` / `-32006` | — | 假服务端记录**调用次数 = 1** | `retryable=false`、message 原样 |
| 14 | 网关 `-32003` | — | 调用次数 = 1 | `retryable=true` |
| 15 | 4xx + JSON-RPC error body | — | — | `error_code` 保留 `-32xxx`，不是 `-1` |
| 16 | 超时（非终态） | — | — | `error_code=-1`、`retryable=true`，detail 含最后状态与 task_id |

配置列写清楚是矩阵能跑起来的前提：第 9/10/11 行各有独立的 allowlist 配置；"不重试"用假服务端的**请求计数**证明，而不是断言不存在的重试代码。

## 6. 风险

- **网关卡片自相矛盾**：`supportedInterfaces[].protocolVersion` 恒为 `1.0`，顶层 `protocolVersions` 保留注册方声明（`presenter.go:86-96`）。协商按接口条目优先，故经网关一律 v1.0；把 v0.3 上游挂到网关后面会被用 `SendMessage` 调用。本轮不修网关，README 记一条。
- **网关 name 路由**（`POST /a2a/name/{agentName}`）没有卡片端点，只能走降级 v0.3；对 v1.0 上游会失败。README 记一条。
- 严格 ProtoJSON v1.0 服务端可能拒绝出站 `role: "user"` / `kind`；本轮不支持（§2 非目标）。
- `0.4.0` 与上游 `0.3.x` 分叉 → README 写明关系；上游修复后优先切回。
