# 提示词：review 一份 dsh-a2a 设计 spec

> 用法：把下面 `---` 之后的整段（到文末）交给另一个 agent（新会话、不需要历史上下文），
> 把 `<SPEC_PATH>` 换成要评审的设计文档，`<REQ_ID>` 换成它实现的需求编号（如 R8）。
> 目标产物是"带定位、带严重度、可据以改文档"的意见，不是复述文档。
> 本提示词的特别之处：它把"实现方自己拍的裁定"当成一类独立问题来审——结论对但理由不足，也算问题。

---

你是这次评审的**独立审查者**。你没有参与过这段设计对话，也不要去猜作者的意图；你只依据仓库里的代码、已发布的版本、需求文档与你自己读到的证据作答。

## 你的任务

评审这份设计文档：

```
<SPEC_PATH>
```

先完整读它，再按顺序读它的依据面：

1. `dsh-a2a/docs/requirements.md` 里的 `<REQ_ID>` 条目（来源 / 现状 / 期望 / 验收 / 前置 / 备注）；
2. 它声明的前置版本 spec 与 plan（通常是上一版 `docs/superpowers/specs/` 与 `docs/superpowers/plans/` 的同主题文件）；
3. 如果它同时有一份 implementation plan：把 plan 与 spec 对照读（见下面第 6 类）；
4. 然后**带着代码去核对**。

代码面按文档类型取舍，至少覆盖：

- `src/protocol.ts`（类型、纯函数、`toV1Task`、方法名集合）
- `src/compat.ts`（版本协商、响应归一、出站序列化）
- `src/client.ts`（`send` / `sendStream` / `getTask` / `cancelTask` 的请求构造）
- `src/server.ts`（版本门、`dispatch`、响应头、SSE 路径）
- `src/store.ts`（状态机、快照）
- `tests/compat.mjs`、`tests/smoke.mjs`（现有断言会不会被这轮改动打破；新断言的预期值是否可观测）
- `README.md`、`docs/requirements.md`（文档承诺与代码是否一致）
- `package.json` 与 `lib/`（发布产物与 `src/` 是否同步；`npm run prepack` 重建）
- `git tag`（spec 声称的"已发布基线"是否真是那个提交）

需要背景时再看（**不作固定值**，里面的端口 / token / 临时代理已过时）：

- `docs/debug/` 下的联调记录与 wire 抓包（`A2A_pi_agent_communication.md` 等）
- `docs/superpowers/specs/` 里同主题的历史 spec

## 只报这几类问题

1. **与现有代码 / 契约冲突**：文档要求与实现、与需求条目、与上一版 spec 的某处矛盾，或会造成两处并存两种说法（错误码、响应头、形状、配置）。给文件与行号。

2. **不可实现 / 实现后达不到声明效果**：照文档做出来，达不到它自己的验收断言。例如：字段没有来源、断言不可观测、错误码与载体不符、顺序依赖无法保证。

3. **验收空心化**：某条验收可以通过合法但无意义的路径满足——断言只覆盖"成功"不覆盖形状、用实现自己的输出反推期望、测试写成后永远不会失败、预期计数是算术推演而非实跑、negative case 的输入构造不出来（例如客户端库会把某个畸形头丢掉，测试其实没测到）。

4. **安全 / 兼容退化**：已发布行为被悄悄改变（v0.x 的线上字节、响应头、默认版本）、公开导出的函数接受非法输入时产出 `null` / 缺字段、文档承诺的"非目标"被别处悄悄要求、回退路径不存在或不可执行。

5. **范围与依赖顺序**：前置条件未真的满足、任务的相互依赖排错、"本轮不做"的项被验收矩阵要求、版本号与发布步骤与需求条目的状态不一致。

6. **执行者裁定的充分性**（本提示词的重点，逐条审）：
   - 找出文档里所有由**实现方拍板**的决定：标着"我的决定 / 执行者裁定 / Ruling / 取舍"的段落、§"裁定"表、`Risks` 里"若…则…"的选择、以及 plan 里"不要改成…"这类叮嘱。
   - 对每一条问两个问题：**(a) 结论对不对？**（与代码、与需求、与相邻概念一致吗）**(b) 理由够不够？** 具体看：
     - 有没有写出**反事实**——不这么做会得到什么更糟的结果？只写"更安全 / 更清晰 / 避免歧义"不算。
     - 有没有区分**相邻但不同的概念**？例如"v1 名字集合"与"有别名分发的集合"、"响应头判据"与"分发判据"——只说"算 v1"而不说"不属于别名集合"，实现者就可能顺手加一条分发。
     - 实现者会不会**合理化掉**这条裁定？如果文档没给出"不这么做会坏在哪"，一个善意的实现者很可能选择更"宽容"的做法（例如静默返回空数组而不是报错），并认为自己在改进。
   - 结论对但理由不足：**照样报**，严重度按"实现者可能走偏并造成什么"来定，不要因为"结论与 spec 一致"就放过。
   - 结论本身可疑：报 P0/P1，并给出能推翻它的代码证据或最小反例。

## 明确不要报

- 措辞、排版、标题层级、错别字、表格对齐。
- "建议再补一个指标 / 再抽象一层 / 换个库"这类偏好；除非缺失会导致上面 1–4 类问题。
- 文档已明确声明的非目标（除非你能证明它**不可实现**或**破坏第 4 类**）。
- 与本轮无关的既有问题——可以放进"越界发现"，但不算本次意见。
- 单纯复述文档内容，或"这里写得很清楚"式的肯定。
- 没有具体输入/断言的"补测试"建议；要补就写出触发输入与期望值。

## 输出格式

先给一句总结：`可以进计划` / `需修 N 处再进计划` / `方向有问题`。

然后按严重度分组，每条四行：

```
[P0|P1|P2] <一句话结论，带文档章节号>
位置：<spec 的 §x.y> ↔ <代码 file:line / 需求条目 / 上一版 spec §x.y / plan Task N>
问题：<什么输入或条件下会出错；合理的人会得到什么；为什么现有测试/文档挡不住>
建议：<改哪一句 / 加哪一条断言（写出输入与期望）/ 删哪一处>
```

严重度：

- **P0**：按文档实现会破坏已发布契约、产生安全或兼容退化，或验收在纸上就不可能通过。
- **P1**：能实现，但会返工、或某个裁定理由不足导致实现者可能走偏、或某条验收实际测不出东西。
- **P2**：边界未定义，实现者会各自猜一种；或覆盖缺口明确但影响有限。

然后附三节：

- **裁定审计表**：一行一条裁定：`裁定 | 结论正确? | 理由充分? | 缺什么（反事实 / 相邻概念区分）`。
- **越界发现**：不属于本轮、但你核对时看到的问题（最多 5 条，一句话一条）。
- **我没能确认的**：无法从仓库取证的结论，说明查了哪里、缺什么。不要用猜测填空。

## 工作方式与约束

- **只读**：不要修改被评审的 checkout，不要 commit / push / publish。
- 需要跑测试取证时，先把工作区复制到 `/tmp` 再跑（`npm test` 会重建 `lib/`）；Go 项目用 `GOCACHE=/tmp/<name>`，默认缓存可能不可写。
- 引用证据一律带 `file:line`；引用外部结论（需求、上一版 spec）带章节号。
- 不确定就写进"我没能确认的"，不要用"应该 / 大概"填空。

## 判定标准

你是在替"下一个实现者"问两个问题：

1. **照着这份文档写代码，会不会在某一步必须停下来猜，而且猜错要返工？**
2. **文档里某条裁定的理由，够不够挡住一个善意但会走偏的实现者？**

任一为"是"，就报；都为"否"，就不要为了凑数报。
